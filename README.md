# Lab03 - Чанарын сценарио → SLO → k6 threshold

Нэр: Ц.Төгөлдөр Оюутны код: B232270050

## Тухай

Энэ төсөл нь жижиг локал Express API (`/cart/add`, `/report`, `/pay`) дээр 3 чанарын сценарио (performance, reliability, availability) бичиж, тэдгээрийг SLO болгон томьёолж, эцэст нь k6 threshold болгон кодчилж автоматаар шалгасан ажил юм. Мөн availability сценариогоо бодитоор турших зорилгоор жижиг chaos experiment хийсэн (серверийг тестийн явцад унагаж, дахин асаах).

## k6 хувилбар

k6 v2.2.0 (commit/00a9a1b7f5, go1.26.5, linux/amd64)

## Ажиллуулах заавар

**Локал API асаах:**
```bash
npm install
node server.js
```

**k6 тестүүд (өөр терминал дээр, сервер ажиллаж байх үед):**
```bash
mkdir -p results
k6 run slo-test.js 2>&1 | tee results/pass.txt        # SLO threshold-той энгийн тест
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt   # Санаатай эвдэрсэн threshold
```

Chaos экспериментийг README-ийн "Мини Chaos Experiment" хэсэгт тайлбарласан алхмуудаар гараар хийнэ.

| **Гадаад өдөөлт** | **ЭВДРЭЛ** — сервер процесс гэнэт зогсоно (Ctrl+C), 10 секундын дараа дахин асна |
| **Шаардлагатай хариу** | Сервер дахин асаагдсаны дараа шинэ хүсэлтүүдийг хэвийн зөв боловсруулна |
| **Хэмжүүр** | Availability (амжилттай хүсэлт / нийт хүсэлт) ≥ 90%; сэргэх хугацаа (recovery time) секундээр |

## SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | Босго сонгосон үндэслэл |
|---|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 5 мс | 20 VU, 1 мин | `baseline-cart.js`-ээр 20 VU-ийн бодит ачааллын дор хэмжсэн суурь p95 = 2.87мс. Үүнийг 1.5-аар үржүүлж (245.89×1.5 хэлбэрийн Lab2-той адил аргачлал) ≈4.3мс гарсныг 5мс болгож дугуйруулсан — жижиг локал endpoint дээр хэмжилтийн хэлбэлзэл харьцангуй өндөр (max=28.86мс-д хүрч байсан) тул бага зэрэг илүү зай авсан. |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 мин | Серверт ~5% алдаа санаатай суулгасан тул 8% бодит зөвшөөрөгдөх дээд хязгаар |
| Availability | Нийт хүсэлтийн амжилтын хувь | ≥ 90% | 2 мин, дунд нь 10с зогсолт | 2 минутын цонхны 10 секундын зогсолт цагаар тооцоход ≈91.7% availability өгөх ёстой (доор тооцоолсон), тул 90%-ийг бодит хэрэгжихүйц, бага зэргийн нөөцтэй (safety margin) босго болгон сонгосон. |

### Error budget тооцоо

2 минутын цонхонд 90% availability гэдэг нь: 120 секунд × (100% - 90%) = **12 секундийн "эвдрэх эрх"** (цагаар тооцсон budget).

Алхам 5-д үүнийг хүсэлтээр дахин тооцож, хоёр тоо яагаад зөрж байгааг доор тайлбарласан.

## Мини Chaos Experiment (`results/chaos.txt`)

**Хийсэн алхмууд:**
1. `slo-test.js`-ийн duration-ийг `'2m'` болгож өөрчилсөн
2. `k6 run slo-test.js 2>&1 | tee results/chaos.txt` эхлүүлсэн
3. Тест ажиллаж байх зуур өөр терминал дээр серверийг Ctrl+C-ээр зогсоосон (~0m40с орчимд)
4. 10 секунд хүлээгээд `node server.js`-ээр дахин асаасан

**Ажиглалт:**
- Зогсолтын үед `http_req_failed{name:pay}` 89.98% (threshold 8%-г мэдэгдэхүйц давсан); ерөнхий `http_req_failed` 89.63% (189,849 / 211,800)
- `checks` хувь 10.53% амжилттай (22,316 / 211,800), 89.46% (189,484) амжилтгүй болсон
- Availability threshold **FAIL** болсон (`checks rate=10.53%` < 90% шаардлага)
- Латенси threshold-ууд (`http_req_duration{name:cart}` p95=240.69µs, `{name:report}` p95=304.71ms) сонин хэрэг **PASS** хэвээр үлдсэн

**Бодит availability тооцоолол (хүсэлтээр):**

Амжилттай хүсэлт / Нийт хүсэлт = 22,316 / 211,800 = 0.1053 ≈ **10.53%**

**Цаг ба хүсэлтийн budget яагаад зөрдөг вэ:**

Логоос харахад connection-refused алдаанууд бүгд 9 секундийн цонход (16:25:40–16:25:48) тохиосон — төлөвлөсөн ~10 секундийн зогсолттой бараг таарч байна. Гэхдээ тухайн 9 секундэд ганцхан 189,484 хүсэлт амжилтгүй болсон нь нийт 211,800 хүсэлтийн дийлэнх хувь юм. Шалтгаан нь: сервер унасан үед холболт татгалзагдах (connection refused) хариу шууд, бараг тэг хугацаанд ирдэг — харин хэвийн үед `/report` 200-400мс хүлээдэг тул VU-ууд циклээ шинэчлэхэд саатдаг. Иймд зогсолтын үед VU бүр секундэд хамаагүй олон удаа хүсэлт илгээж чаддаг болсон тул тухайн 9 секунд нь ердийн 9 секундээс хамаагүй олон "хүсэлтийн орон зай" эзэлдэг. Үүний үр дүнд цагаар тооцсон 12 секундийн budget (120с × 10%) бол ердийн ачааллын хурдаар тооцсон тул бодит байдалд ажиглагдсан 89%-ийн request-based алдаатай зэрэгцэхгүй — цагаар тооцсон тоо бодит хэрэглээний эрсдэлийг дутуу үнэлдэг гэдгийг энэ туршилт тод харуулж байна.

**Reliability threshold мөн эвдэрсэн үү:**

Тийм — `http_req_failed{name:pay}` 89.98%-д хүрч, 8%-ийн threshold-ыг эрс давсан. Учир нь сервер бүрэн унасан үед `/pay`-ийн ЯМАРЧ хүсэлт хариу авдаггүй (connection refused), харин `http_req_failed` метрик нь энэ төрлийн бүрэн хариугүй байдлыг ч, серверийн санаатай буцаадаг 500 статусыг ч ялгаагүйгээр "амжилтгүй" гэж тооцдог. Тиймээс бүрэн доголдол (outage) нэг мөчид availability (`checks`) болон reliability (`http_req_failed{name:pay}`) хоёр SLO-г зэрэг эвдэж чадна; эдгээр хоёр SLI-г ялган харах боломж зөвхөн серверийн хэсэгчилсэн доройтол (жишээ нь удаашрал, эсвэл зөвхөн заримдаа гарах 500) үед л бодитоор ажилладаг бөгөөд бүрэн crash-ийн үед хоёул нэгэн зэрэг унадаг.

## Дүгнэлт

Энэ лабораторийн ажлаас хамгийн хэцүү санагдсан алхам бол сценариог тоон SLO болгож хувиргах хэсэг байсан — ялангуяа availability-г "хугацаагаар" уу, "хүсэлтээр" үү гэдгийг тодорхойлох, учир нь эдгээр хоёр өнцгөөс тооцоолол эрс өөр хариу өгдгийг эхлээд ойлгоход хэцүү байлаа. Threshold-уудыг таамгаар биш, `baseline-cart.js`, `baseline-report.js`, `baseline-pay.js` зэрэг бодит 20 VU ачааллын дор хэмжсэн k6 файлаас гаргаж авсан нь Lab2-ийн туршлагаас сурсан хамгийн чухал зүйл байлаа — таамагласан тоо бодит ачааллын нөхцөлтэй үргэлж давхцдаггүй гэдгийг дахин баталгаажуулсан. Chaos туршилт миний availability сценариог бүрмөсөн батлаагүй ч, үгүйсгээгүй — харин илүү нарийвчилсан, зарим талаараа гайхмаар зураг харуулсан: цагаар тооцсон 12 секундийн error budget нь бодит хэмжсэн ~89%-ийн request-based доголдолтой (10.53% availability) огт давхцаагүй. Энэ зөрүүний шалтгаан нь сервер унасан үед холболт татгалзах хариу шууд ирдэг тул VU-ууд секундэд хамаагүй олон хүсэлт илгээж чаддагт оршино гэдгийг лог файлын timestamp шинжилгээгээр батлан харуулсан. Мөн латенси threshold-ууд (cart, report) chaos-ийн үед сонин хэрэг PASS хэвээр байсан нь маш чухал сургамж өгсөн: латенси хэмжүүр ганцаараа системийн бүрэн доголдлыг илрүүлж чаддаггүй, учир нь амжилтгүй холболтууд "удаан" биш, харин зөвхөн "амжилтгүй" тул latency percentile-ийг бүр доошлуулдаг. Ийм учраас availability/error-rate болон latency threshold-уудыг хамтад нь, нэгийг нөгөөгөөр орлуулахгүйгээр ашиглах шаардлагатайг энэ туршилт тодорхой харуулсан.

## Аюулгүй байдлын анхаарал

Энэхүү тестийг зөвхөн локал машин дээрх өөрийн сервер (`localhost:3000`) руу л ажиллуулсан. Ямар ч бодит вебсайт эсвэл гуравдагч этгээдийн сервер рүү load тест хийгээгүй.
